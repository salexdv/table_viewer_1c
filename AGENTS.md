# Правила работы с table_viewer

## Назначение

Проект собирает автономный HTML-просмотрщик таблиц и деревьев значений для «Поля HTML документа» 1С 8.3.14+.
Код, комментарии, спецификации и документация ведутся на русском языке.

## SDD

Любая новая функция, изменение поведения, публичного API, событий 1С или формата сборки начинается со
спецификации в `specs/<id>/spec.md` и плана в `specs/<id>/plan.md`.

Статусы: `draft` → `approved` → `in-progress` → `done`. Код разрешено менять только после `approved`.
Расхождение реализации со спецификацией исправляется в том же коммите. Завершённая спецификация переносится
в `specs/done/<id>/`.

## Ограничения реализации

- Публичные функции интеграции экспортируются непосредственно на `window`.
- Обратный мост 1С сохраняет контракт `{ event, params }` в `window.events_queue` и передаёт его через
  `clickEvent.eventData1C` скрытой кнопки `#event-button`.
- Production-сборка — один self-contained `dist/index.html`, без внешних ресурсов и сетевых запросов.
- ES-floor — ES2015. Не использовать optional chaining, nullish coalescing и API, отсутствующие в старом WebKit,
  без совместимого fallback.
- Данные выводятся только через `textContent`; запрещены `eval`, `Function` и вставка пользовательского HTML.
- Состояние интерфейса живёт только в памяти документа.

## Релизы и история изменений

- Релизами управляет Release Please из ветки `master`. Не создавать теги и GitHub Releases вручную, не
  изменять версии в `package.json`, `package-lock.json` и `.release-please-manifest.json`, а также не вести
  `CHANGELOG.md` вручную: эти файлы обновляются в Release PR.
- Все коммиты оформлять как Conventional Commits: `<type>(<scope>): <краткое действие на русском языке>`.
  Scope необязателен, но должен обозначать устойчивую область проекта, например `search`, `tree`, `grid`,
  `api`, `build` или `release`.
- Subject должен точно описывать одно законченное изменение и быть пригодным для release notes. Использовать
  русскую формулировку действия: `добавить`, `исправить`, `сохранить`, `ускорить`, `описать`. Не использовать
  бессодержательные сообщения вроде `update`, `changes`, `правки`, `fix` или `misc`.
- `feat:` означает новую пользовательскую возможность и повышает minor-версию; `fix:` означает исправление
  пользовательского дефекта и повышает patch-версию. Несовместимое изменение помечать `!` после type/scope
  и подробно описывать в footer `BREAKING CHANGE: <описание на русском>` — оно повышает major-версию.
- Для внутренних изменений выбирать точный type: `perf`, `refactor`, `docs`, `test`, `build`, `ci`, `chore`
  или `style`. Не маскировать служебное изменение под `feat`: заголовки `feat` и `fix` попадают в
  пользовательский changelog и определяют следующую версию.
- Если одного subject недостаточно, в body по-русски объяснить причину, выбранное решение и существенные
  последствия. Не объединять независимые изменения в один коммит.
- Примеры: `feat(search): добавить поиск по упорядоченным фрагментам`, `fix(tree): сохранять раскрытие при
  фильтрации`, `perf(grid): переиспользовать строки виртуальной таблицы`, `docs(api): описать восстановление
  настроек`.
- Footer `Release-As:` использовать только для явно согласованной разовой версии. Обычный релиз выполняется
  слиянием подготовленного Release Please PR после проверки версии, changelog и release assets.

## Команды

- `npm run dev` — webpack-dev-server.
- `npm run build` — production single-file сборка и её проверка.
- `npm run test:unit` — unit-тесты модели.
- `npm run test:browser` — интеграционный smoke в Chromium.
- `npm test` — полный локальный гейт.

Перед коммитом запускать релевантные проверки. После каждого значимого завершённого этапа создавать отдельный
коммит с сообщением Conventional Commits.
