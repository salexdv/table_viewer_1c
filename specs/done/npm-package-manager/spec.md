# npm-package-manager: Переход с pnpm на npm

## 1. Контекст и проблема

Проект использует pnpm как менеджер пакетов, хотя сборка не зависит от его специальных возможностей. Для
уменьшения числа обязательных инструментов проект должен устанавливаться, собираться и проверяться стандартным
менеджером npm, поставляемым вместе с Node.js.

## 2. Область изменений

Изменяются сценарии `package.json`, lock-файл, инструкции для разработчиков и документация сборки. Исходный код
просмотрщика, production-формат `dist/index.html`, публичный JavaScript API и события 1С не изменяются.

## 3. Поведение

### 3.1. Основной сценарий

1. Разработчик устанавливает Node.js 20+ с npm.
2. Команда `npm install` устанавливает версии зависимостей, зафиксированные в `package-lock.json`.
3. Команды `npm run dev`, `npm run build`, `npm run test:unit`, `npm run test:browser` и `npm test` выполняют
   существующие сценарии проекта.
4. Одноразовые CLI-пакеты запускаются через `npx`.

### 3.2. Граничные случаи и ошибки

- Отсутствие Node.js остаётся ошибкой окружения: переход на npm не позволяет запускать Webpack без `node`.
- Установка в CI может выполняться через `npm ci` по зафиксированному lock-файлу.
- В репозитории не поддерживаются одновременно lock-файлы npm и pnpm.

## 4. Публичные контракты

Менеджер пакетов проекта — npm. Репозиторий содержит `package-lock.json` и не содержит `pnpm-lock.yaml`.
Публичные контракты приложения и production-сборки не меняются.

## 5. Критерии приёмки

- [x] `package.json` не вызывает pnpm и фиксирует npm как менеджер пакетов.
- [x] `package-lock.json` создан, `pnpm-lock.yaml` удалён.
- [x] README, документация интеграции и инструкции репозитория используют команды npm/npx.
- [x] Поиск по рабочим файлам не находит устаревших команд pnpm.
- [x] Доступные unit-, build- и browser-проверки проходят через npm.

## 6. Вне области

- Изменение версий прикладных зависимостей.
- Изменение автономного HTML или поведения просмотрщика.
- Установка Node.js в пользовательскую операционную систему.
